# Scentify Input-Validation Audit Findings

Audit basis: the current source tree at `/mnt/Storage/scentify`, `AGENT_TASKS.md`, and `CONTEXT.md`. The mounted `.git` directory is unusable, so the current tree is authoritative. This report reflects the reviewed follow-up fixes. Status labels describe implementation/review state; Flutter widget tests and Firestore Rules tests are authored but could not run in this environment.

## Findings

### Open findings and policy-dependent risks

High — F-01 | Cloud Functions, `functions/index.js:createPayMongoCheckoutSession` and `getOrderReview`: a same-user review can be refreshed with the same `orderId` while PayMongo session creation is awaiting `fetch`, because the intent is written only after the response and the refresh transaction sees no order or intent yet. A session may then be bound to an ID whose current review describes another quote, leaving the client unable to create a matching order or the callback without a matching order. Evidence: the payment callable reads the review before `fetch` and writes `checkoutIntents/{orderId}` afterward; same-user pre-binding refresh is deliberately supported and its test is sequential. Proposed fix: decide whether refresh remains supported, then bind/reserve the quote before the provider call or make IDs single-use, with cleanup/expiry for failed reservations. Status: waiting on a policy decision.

Medium — F-02 | Cloud Functions, `functions/index.js:confirmPaidOrder`: a matching signed `checkout_session.payment.paid` event is not checked against `intent.status`, `intent.expiresAt`, or an authoritative provider payment-time before confirming the order. A callback can therefore be accepted after local intent expiry if the order remains pending; whether PayMongo can produce such a late event is not established. Evidence: the transaction verifies order/intent/review identity and amount but does not inspect intent state or expiry. Proposed fix: confirm PayMongo’s authoritative payment-time semantics, then define whether late payments are confirmed, rejected, or manually reconciled; do not rely on webhook receipt time alone because delivery can be delayed. Status: waiting on a policy decision.

Medium — F-03 | Cloud Functions, `functions/index.js:getOrderReview` and `deliveryOptionById`: `same-day` is accepted for any otherwise valid address, not only Metro Manila. Evidence: `CONTEXT.md` labels the option Metro Manila only, while the server maps the delivery ID/fee without checking the resolved city or province. Proposed fix: enforce a server-side area allowlist after the eligible locations and canonical name/alias matching are defined. Status: waiting on a policy decision.

Medium — F-04 | Frontend, Cloud Functions, and Firestore Rules, phone validation: any nonblank string up to 32 characters, including `abc`, is accepted as a phone number. Evidence: `normalizeReviewAddress` uses a length-bounded `readString`, `validAddressShape` checks only nonblank text/length, and the form only selects a phone keyboard. Proposed fix: define supported Philippine phone formats and normalization before applying the same policy at all layers. Status: waiting on a policy decision.

Medium — F-05 | Firestore Rules, `firestore.rules:/carts/{userId}`: a client can still directly write up to 100 arbitrary nested cart list members, even though callable paths reject malformed carts. Rules constrain root keys/list type/size but cannot iterate each member to validate fields, IDs, quantities, or duplicates. A malformed direct write can still break strict Flutter cart decoding; checkout rejects it rather than silently filtering it. Evidence: nested checks exist in `functions/index.js:addToCart` and `getOrderReview`, not in the rule. Proposed fix: if Rules-level enforcement is required, authorize a write-path/storage redesign (for example, callable-only writes or per-item documents); otherwise retain the explicit limitation and callable validation. Status: waiting on a policy decision.

Low — F-08 | Frontend/backend review text, `lib/main.dart` review dialog and `functions/index.js:submitProductRating`: the UI limit counts grapheme clusters while JavaScript `String.length` counts UTF-16 code units; for example, 600 emoji can pass the UI’s 1,000-character cap but exceed the backend’s 1,000-unit cap. Evidence: UI `maxLength` is 1,000 and backend `readString` compares JavaScript `.length`. Proposed fix: align the client/server length unit and add a supplementary-character test. Status: deferred.

Low — F-09 | Firestore Rules, `firestore.rules:/wishlists/{userId}`: direct client writes can still include arbitrary `productIds` values/strings up to the list limit because Rules cannot iterate a variable-length list. The normal repository validates IDs and filters invalid legacy strings, but a malicious direct Firestore write bypasses that client-side check. Evidence: Rules validate only the root key, list type, and size; repository checks are in `firestore_wishlist_repository.dart`. Proposed fix: use a trusted callable or per-item storage if server-enforced member validation is required; otherwise retain this documented trust-boundary limitation. Status: waiting on a policy decision.

Low — F-10 | Firestore Rules and catalog decoding, `firestore.rules:/perfumes/{productId}` and `lib/core/firebase/firestore_codecs.dart:perfumeFromMap`: admin writes have no document-shape validation, so malformed published fields or unsupported enums can be stored; the strict codec can then throw while listing/watching the catalog. The documented admin UI is read-only, but an authenticated admin client can still write through Rules. Proposed fix: validate the catalog schema at an admin write boundary or keep catalog writes server-managed. Status: deferred.

Low — F-12 | Frontend/backend postal-code contract, `ShippingAddress` and `functions/index.js:normalizeReviewAddress`: `" 1100 "` is rejected by the model and Firestore Rules but accepted by direct checkout because backend `readString` trims before validating and stores `1100`. This is an inconsistency, not a bypass of postal-code content validation. Proposed fix: choose one trim/reject contract and apply it consistently. Status: deferred.

### Fixed findings

High — F-13 | Cloud Functions, `functions/index.js:getOrderReview` and `createPayMongoCheckoutSession`: cross-user review-ID reuse and snapshot mutation after an order/intent binds an ID are rejected; the payment callable verifies quote ownership/snapshot equality. Evidence: Functions tests cover cross-user reuse, mismatched review IDs, and mutations after order/intent binding. Same-user refresh before binding remains intentionally supported and is covered by F-01. Proposed fix: bind review ownership and immutable snapshots to the order/intent; implemented and reviewed. Status: fixed and verified.

Medium — F-14 | Cloud Functions, `functions/index.js:addToCart`, `selectedCartItems`, and `getOrderReview`: quantities over 100, including accumulated line quantity and omitted-selection cart quantity, are rejected. Evidence: `MAX_CART_ITEMS = 100` and boundary tests. Proposed fix: enforce the bound on every quantity path; implemented and reviewed. Status: fixed and verified.

Medium — F-15 | Cloud Functions, `functions/index.js:addressAutocomplete` and `addressPlaceDetails`: rotating caller-controlled `sessionToken` values no longer reset a user’s rate limit because limiting is UID-keyed. Evidence: tests exhaust each UID budget with distinct tokens and verify the next request is rejected. Proposed fix: scope abuse limits to authenticated UID; implemented and reviewed. Status: fixed and verified.

Medium — F-16 | Cloud Functions, `functions/index.js:readEnum` and `readPaymentMethod`: noncanonical casing/whitespace values such as `GCASH`, `php`, `" MANUAL "`, and `" standard "` are rejected rather than normalized. Evidence: table-driven Functions tests. Proposed fix: validate exact wire values; implemented and reviewed. Status: fixed and verified.

High — F-17 | Cloud Functions, `functions/index.js:confirmPaidOrder`: replaying a processed signed webhook no longer repeats stock or rate-limit writes because event lookup and side effects share a Firestore transaction. Evidence: sequential replay test confirms stock changes once and the limiter count remains one in serialized fake Firestore. Proposed fix: make replay detection and side effects atomic; implemented and reviewed. Status: fixed and verified.

High — F-18 | Firestore Rules, `firestore.rules:/orders/{orderId}`: orders with mismatched review/intent ownership, totals, references or methods, expired review/intent, extra keys, forged provider claims, or nonempty initial events are denied. Evidence: `validOrderShape`, `validOrderReview`, `validCheckoutIntent`, `validSandboxOrder`, and the Rules denial matrix. Proposed fix: require exact order shape and quote/payment binding; implemented and reviewed. Status: fixed and verified.

Medium — F-19 | Firestore Rules, `firestore.rules:/carts/{userId}`: client writes can no longer forge `serverConfirmed`, `lastOperationId`, or `serverConfirmedAt`; root client fields are allowlisted. Evidence: the cart-marker denial test. Proposed fix: restrict client-writable root fields; implemented and reviewed. Status: fixed and verified.

Medium — F-20 | Firestore Rules, `firestore.rules:validAddressShape`: saved addresses reject blank/format-only required text (including U+200B cases), unsafe `placeId`s, partial coordinate pairs, and out-of-range coordinates while allowing null location fields. Evidence: table-driven address, ID, and coordinate denial cases. Proposed fix: validate required text, ID syntax, and coordinate pairs/ranges; implemented and reviewed. Status: fixed and verified.

Medium — F-21 | Cloud Functions, `functions/index.js:isCartItem`, `addToCart`, and `getOrderReview`: malformed nested cart entries (including null/non-string/unsafe IDs, extra keys, invalid quantities) and duplicate product/variant lines are now rejected instead of filtered or collapsed; `addToCart` validates before idempotent return/write and preserves the full cart on failure. Evidence: Functions tests cover the malformed matrix, duplicate rows, matching idempotency marker, full-document nonmutation, and valid add/replay. Proposed fix: fail closed on invalid stored cart state; implemented and reviewed. Status: fixed and verified.

Medium — F-22 | Frontend address form, `lib/main.dart:CheckoutAddressPage`: overlong address fields now produce field errors before save/checkout, using the established server/rules caps. Evidence: widget/integration tests cover caps and overlong programmatic autocomplete values; Reviewer approved. Proposed fix: match UI validation to the server contract; implemented and reviewed. Status: fixed and verified.

Medium — F-23 | Frontend address editing, `lib/main.dart:CheckoutAddressPage`: editing or selecting a saved address previously constructed a `ShippingAddress` with empty `notes`, erasing stored notes on save or dropping them from checkout. The form now carries notes through saved-address paths and clears them only for a new address; tests cover preservation and reset. No delivery-instructions UI was added. Proposed fix: preserve existing stored data without expanding the UI; implemented and reviewed. Status: fixed and verified.

Medium — F-24 | Frontend auth/profile, `lib/main.dart` and `firestore.rules:/users/{userId}`: registration names are rejected before Firebase Auth creation when over 120 characters; provider-supplied long names fall back safely; profile editing enforces the same cap before write/pop and retains invalid input for correction. Evidence: registration/profile widget tests and Reviewer’s source/test review. Proposed fix: enforce the profile rule at every name-entry/auth path; implemented and reviewed. Status: fixed and verified.

Low — F-25 | Wishlist repository, `lib/features/wishlist/data/firestore_wishlist_repository.dart`: normal repository writes now reject malformed/overlong product IDs and more than 100 IDs; reads filter invalid legacy string IDs so they do not block future toggles. Evidence: repository tests cover validation, legacy cleanup, and list limit. Direct Firestore writes remain the separate Rules limitation in F-09. Proposed fix: validate and recover at the repository boundary; implemented and reviewed. Status: fixed and verified.

Low — F-26 | Firestore Rules, `firestore.rules:/users/{userId}/addresses/{addressId}`: owner writes are now restricted to `addressId == 'primary'`, matching the current repository and documented single-address model; secondary create/update/delete are denied while owner reads remain allowed for legacy documents. Evidence: Rules denial test. Proposed fix: align writable IDs with supported storage model; implemented and reviewed. Status: fixed and verified.

## Code/document drift

- `CONTEXT.md` says same-day delivery is Metro Manila only; server-side destination enforcement is still absent (F-03).
- `CONTEXT.md` calls carts shape-validated; callable paths validate nested rows, but direct Rules writes only validate root keys/list size (F-05/F-21).
- `CONTEXT.md` lists a 30-minute intent TTL; webhook confirmation does not enforce intent status/expiry or provider payment time (F-02).
- Postal-code whitespace handling differs across Flutter, Rules, and direct checkout input (F-12).
- The single saved-address path now matches repository and Rules writes; delivery instructions remain deferred and existing notes are preserved (F-23).

## Open policy decisions

1. **Same-ID quote refresh and PayMongo fetch race (F-01).** Option A: keep pre-binding refresh but serialize/bind the quote before awaiting PayMongo, with reservation timeout/release behavior. Option B: make quote IDs single-use and require a fresh ID for each changed quote. Option C: preserve current behavior and accept risk of a provider session detached from the final review/order.
2. **Late PayMongo payments (F-02).** Option A: accept any matching signed paid event after local TTL. Option B: compare a verified authoritative provider payment time with intent expiry and hold/reconcile late or timestamp-less callbacks. Receipt time alone is unsafe because callbacks may be delayed; provider field semantics must be confirmed first.
3. **Same-day coverage (F-03).** Option A: enforce Metro Manila and supply its canonical city/municipality/alias list. Option B: explicitly list additional eligible areas, changing documented coverage.
4. **Philippine phone formats (F-04).** Define local/international formats and normalization (or explicitly retain nonblank-text-only validation); each option changes false rejection versus acceptance of unusable values.
5. **Nested cart/wishlist Rules validation (F-05/F-09).** Option A: retain direct client writes and accept that Rules cannot validate list members; callable paths/repository provide partial protection but malicious direct writes remain possible. Option B: route writes through trusted callables and deny direct writes, requiring client API changes. Option C: use per-item documents so Rules can validate each path/document, requiring a storage migration. No per-item Rules workaround exists for the current variable-length lists.
